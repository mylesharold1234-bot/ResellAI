# Real-World Validation V1

This offline tool audits the existing identification output, production listing normalizers, matching rules, and pricing engine. It does not call APIs, spend credits, change daily snapshots, alter app pricing, or produce new identifications. The previous [Comparable Quality](COMPARABLE-QUALITY.md) and [Pricing Intelligence V1](PRICING-INTELLIGENCE-V1.md) benchmarks use controlled cases and are not interchangeable with this evaluation.

## Collect the data

Start with a 10-product pilot to validate labels and capture handling; aim for 50–100 independently labeled real products before using the results for decisions. A practical 60-product target is 20 footwear, 10 apparel, 15 electronics, and 15 other items. Deliberately include near-identical releases, high/mid/low variants, adult and youth sizes, multiple conditions, bundles and accessories, hard cases with missing metadata, and easy controls. Keep a fixed manifest of intended cases, including identification and provider failures.

1. Obtain permission to use one product photo per case and retain its private reference. Establish the identity from independent evidence such as a legible model/size label, manufacturer record, or documented purchase, not the app answer. Use reviewer IDs rather than names. Record the exact model, category, size/sizing system where applicable, condition, optional verified identifier, and evidence reference. For cases where size is unavailable or inapplicable, record null for both size fields.
2. Write comparable rules before viewing app results: same product, acceptable variants, size group/tolerance, condition or grade, included components, and marketplace/currency. Freeze these rules. A reviewer who did not see model answers should label the product and listing candidates; double-review a subset and adjudicate disagreements. Keep uncertainty rather than guessing.
3. Record the application's actual identification output before any user corrections. Capture authorized production provider responses before normalization, matching or pricing. Record unsuccessful attempts with a reason; leave genuinely unattempted providers absent. Save the exact pages in request order for the searches that were actually run. Preserve provider warnings for partial searches. Daily snapshots and dashboard tables are post-filtered and cannot substitute for these captures. Collection is manual: use an approved provider export or an authorized local development capture; this tool does not fetch or scrape any source. Keep only the fields needed by the existing normalizers, strip unnecessary raw data and personal data, and retain stable seller pseudonyms if needed to replay seller diversity. Do not store API tokens, headers, uploaded image bytes, or private seller data in manifests.
4. For each provider, independently label each sampled listing ID as relevant, irrelevant, or uncertain and record why and the evidence reference. To measure end-to-end recall, also build an independent comparison pool using authorized sources, including relevant items that the original search never retrieved. Where you only reviewed returned candidates, declare retrieved-only. Annotate missing information as uncertain and do not count it as a negative. Keep the capture window and judgment pool aligned.
5. If authorized verified completed sales exist, record only matching same-marketplace transactions, with sale date, item-only USD amount, and evidence of authorization, verification and comparable criteria. Do not infer prices from active listings, undisclosed accepted offers, canceled orders, or list prices. Skip this step if reliable sales are unavailable.

## Manifest format

Copy the two empty starter files from evaluation/ into a private directory (evaluation/private/ is ignored by Git). Both are JSON documents with schemaVersion = 1, a shared datasetId, kind = real, and a cases array. Synthetic fixtures must declare kind = synthetic. The CLI validates required types, unique IDs, allowed providers, and manifest joins. Provenance fields are reviewer attestations, not automatically verified.

| File | Required fields per case | Notes |
|---|---|---|
| Labels | id, category, source, reviewer, photoRef, verifiedIdentity, verifiedModel, size, sizeSystem, condition, criteria, accepted, judgments | verifiedIdentifier is optional. accepted maps identification output field names to independently established accepted aliases. model and category are required; brand, productName, colorway, visibleCondition, and identifyingInformation are optional. Score only fields independently verified and meaningful for the input. |
| Labels → judgments.ebay / judgments.mercari | pool, labels | pool is independent or retrieved-only. Each label has id (exact provider ID, eBay IDs include their version/variation component), verdict, reason, evidence. Each optional sales entry has id, price, currency, basis, soldAt, evidence, authorized, verified, and meetsCriteria. The supported basis for error is item-only. |
| Captures | id, identification, markets | identification is {status:"ok",output:<actual API identification object>} or {status:"error",reason:<recorded failure>}. Optional details must match the app's matching-detail contract and reflect inputs actually submitted, never gold attributes. For a photo-only evaluation leave details absent unless the app actually submitted details; separate user-refined runs into another manifest. |
| Captures → markets.ebay / markets.mercari | status, capturedAt, pages | Dates use UTC ISO timestamps. On success, pages holds the actual authorized eBay Browse itemSummaries or API.SH Mercari items response objects, in request order (up to four eBay pages, one Mercari page by default, at most two with the opt-in alias fallback). On error use pages:[] and record reason. Optional warnings list partial-stage warnings. Missing provider key means unattempted/unrecorded. |

Size is captured in gold and comparable rules; the current identification contract does not output a standalone size, so the evaluator does not claim size identification accuracy or score a user-entered size as AI output. Visible condition is scored only against explicitly accepted labels; write aliases before looking at predictions. Keep duplicate photo/item identities out of the held-out set when using a development split.

## Run and interpret

From the ResellAI project directory:

    npm run validate:real -- evaluation/labels.template.json evaluation/captures.template.json evaluation/baseline

With data, substitute the two populated files and a private output directory. The script writes report.md and report.json plus input and engine source fingerprints. Keep the inputs immutable and compare engine revisions on the same captures. This freezes retrieval: a change to query generation requires a new, separately tracked capture to evaluate it.

- **Identification accuracy:** exact after case/punctuation normalization or a predeclared alias; missing and incorrect predictions are separate. Unrecorded attempts do not count as wrong answers. A failed identification is a recorded failure and blocks both marketplace recommendations.
- **Match and cohort precision:** true positives divided by judged positives selected, with judgment coverage reported separately. An uncertain/unlabeled prediction does not become a false positive. The cohort metric evaluates listings the pricing engine retained, even if it withheld a price.
- **Recall:** within-capture recall measures relevant normalized candidates selected; independent-pool recall also includes independently found relevant listings not retrieved. Neither estimates recall against all marketplace inventory.
- **Recommendation coverage:** supported recommendations divided by recorded attempts, including recorded provider or identification failures. Successful-capture-only coverage and category breakdowns are in JSON.
- **Pricing reliability:** MAE, mean absolute percentage error and signed bias compare the displayed asking recommendation against the median of at least three distinct authorized verified comparable same-marketplace sales from the previous 90 days. This is retrospective agreement, not a prediction of sale price. Missing sales or recommendation yields no error metric.
- **Failure analysis:** inspect identification field errors, retrieval gaps, incorrect/missed matches, cohort membership, price spread, blockers, provider errors and missing captures. Start improvement work with errors that recur across independently labeled products rather than tuning against one result.

The starter baseline has zero labeled real products and zero captures. Its metrics are unavailable, not 0% accuracy. No paid requests were used to generate it.

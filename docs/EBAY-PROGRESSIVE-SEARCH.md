# Progressive eBay search: implementation and live route verification

Verified 2026-10-19. This supersedes the single-query architecture described in EBAY-COMPARABLE-DIAGNOSTICS.md.

## Failure trace and root cause

The identified action in identification-workflow.ts copied SKU-shaped AI identifyingInformation into details.productIdentifier. There was no independent verification state, even though the input label called the identifier verified. LiveReport sent those details to POST /api/marketplaces/ebay; parseMatchDetails preserved the identifier; buildEbayQuery appended the identifier, colorway/variant, size and packaging to the only Browse query. matchComparable then required the identifier in the listing title. A broad standalone diagnostic had empty details, so it did not exercise the restrictive request generated by a real identification.

This explains the code path that could retrieve one specific result and reject it for identifier mismatch. The original failing HTTP request/response was not retained, so its exact SKU/query cannot honestly be reconstructed. No evidence of a cache collision or pagination bug was found: the previous key included the full request, and only the first page of 100 was intentionally requested. Search construction, automatic trust of inferred identifiers, and conflation of matching with retrieval were the problems addressed.

## New request flow

Image identification and correction remain intact. AI identifyingInformation stays visible as an observation, but no longer populates the verified identifier. The user can enter an identifier and separately check that it was verified on the item/packaging. Editing it clears verification. Legacy requests without the new boolean treat identifiers as unverified.

Stage A searches a recognizable product name and brand, without optional details. Stage B adds recognized visual colors. Stage C uses an applicable naming alias. Duplicate queries are skipped. Stage D adds a user-verified identifier only. Broad evidence is retained even if a specific stage finds nothing. Searches stop early at five exact matches and are bounded at four requests of 100 results; no pagination or automatic retries. The fixed-price and US delivery filters remain; size, condition and packaging no longer suppress basic retrieval.

Results are validated, deduplicated by eBay item ID across stages, and classified exact/close/related. Same-model detail mismatches remain close with reasons, not exact-price inputs. Distinct console/phone editions can be related context. Unrelated models, incompatible shoe silhouettes, accessories, bundles and counterfeit-indicating titles are excluded. Seller-defined unresolved variations display but do not contribute to statistics. Missing condition data is visible and cannot establish condition-matched pricing. A LEGO theme without a set number is related context only.

A median uses exact evidence if available; otherwise only eligible close evidence matching supplied attributes. Related listings, unresolved variations and attribute mismatches are excluded. Low-count listings remain visible. An indicative observed asking range requires at least three eligible prices with spread no greater than 2x. Recommendations require at least five exact listings, three known sellers and the existing condition, identification confidence, size/release (for shoes), production and price-spread safeguards. Specific electronics do not require shoe identifiers. No sold prices or expected-sale prices are inferred.

The existing five-minute cache, in-flight coalescing, two-concurrent-search cap, cooldown handling and hourly request budget remain. Each upstream search stage now consumes the hourly budget. Cache keys are versioned SHA-256 references over identity/details; credentials and tokens never enter logs. Request parameters, counts, grouped exclusions and cache reference are returned in searchDiagnostics and logged server-side using only sanitized product queries. Partial later-stage errors preserve earlier valid evidence with an explicit warning.

## Remaining limits

Title evidence is not a proof of authenticity or exact variant. Only the first 100 results of each bounded query are examined, with no claim of complete market coverage. Different unspecified sizes/conditions/releases can remain visible as close context; descriptive asking evidence is low quality and cannot establish sell-through or achieved sale prices. A theme-only LEGO query needs a specific set number for valuation. The old one-listing response is unavailable for forensic reconstruction. Existing design tokens, uploaded photo workflow, OpenAI API and Facebook permission gates are unchanged.

Final validation: 75 tests passed, TypeScript passed, optimized production build passed. A repeated identical real dashboard request returned cached=true with 227 retained Jordan listings, confirming reuse of the original cached snapshot rather than another Browse search.
